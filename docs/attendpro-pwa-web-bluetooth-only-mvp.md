# AttendPro: чистый PWA (Web Bluetooth) без нативных приложений — анализ реализуемости

**Дата:** 2026-09-21
**Статус:** решение по вопросу «можно ли законченный MVP сделать одним PWA на Web Bluetooth для iOS и Android»
**Контекст:** развивает `attendpro-ble-first-v4.md` (§6–7, §11 C1/C2); проверено против текущего кода MVP (`attendpro/transport/transport.ts`, `hub/server.cjs`).

---

## 1. Короткий ответ

**Полностью кроссплатформенного «одно PWA и ничего больше» не существует — блокирует Apple, а не мы.**

- **Android + десктоп (Chrome/Edge/Samsung Internet): да, чистое PWA реализуемо и у нас уже на 90% готово** — транспорт `Web Bluetooth` в коде есть, роль студента central-only (GATT-клиент), которую Web Bluetooth умеет полностью.
- **iOS (Safari/PWA): нет.** WebKit не реализует Web Bluetooth и не планирует (Apple отказывается годами из-за privacy-позиции). Ни установленная PWA, ни Safari не дадут доступ к BLE — это ограничение платформы, не нашего кода.

Следствие: «полноценный законченный MVP без единого нативного приложения» достижим только в одной из трёх конфигураций (§5), и каждая имеет цену.

## 2. Матрица поддержки Web Bluetooth (проверяемые факты)

| Платформа / браузер | Web Bluetooth (central) | Наш флоу работает? |
|---|---|---|
| Android · Chrome | ✅ | ✅ (уже реализовано, `web_make`) |
| Android · Samsung Internet | ✅ | ✅ |
| Android · Firefox | ❌ | ❌ |
| iOS/iPadOS · Safari (вкл. установленную PWA) | ❌ никогда | ❌ |
| iOS · Chrome/Firefox/Edge | ❌ (все на WebKit — политика Apple) | ❌ |
| iOS · сторонний BLE-браузер (**Bluefy**) | ⚠️ да, кастомная реализация | ✅ проверено на нашем коде (требует установки Bluefy из App Store) |
| macOS/Windows/Linux · Chrome | ✅ | ✅ |

Что Web Bluetooth умеет в нашей роли студента (и что мы уже используем):

- скан через `requestDevice({ filters: [{ services: [UUID] }] })` — системный пикер вместо фонового скана (требует user gesture — наш one-tap «Отметиться» им и является);
- GATT connect / read / write / notify — весь наш цикл `F1 → F2 → F3`;
- фрагментация до 20 байт обязательна (MTU не поднимается из API) — `ble_pack_chunks` уже шлёт фреймы по 18 байт payload.

Чего Web Bluetooth **не умеет** и нам не нужно: peripheral-роль, фоновый скан, advertising. Студент не рекламируется (принцип v4 §5.1) — поэтому студентский путь целиком ложится в Web Bluetooth. **Хаб преподавателя через Web Bluetooth сделать нельзя в принципе** — он должен быть peripheral, а стандарт эту роль не даёт ни на одной платформе (v4 §6 уже это фиксирует).

## 3. Что мешает «просто открыть страницу» — чек-лист PWA-режима

1. **Secure context.** Web Bluetooth и WebCrypto работают только на `https://` (или `localhost`). Наш HTTP-хаб на LAN-IP даёт белый экран — уже поймали на iPhone. Нужно: TLS-хаб (`TLS_CERT`/`TLS_KEY` уже поддержаны сервером) + понятный детект «нет crypto.subtle» с человеческим сообщением вместо белого экрана.
2. **Сертификат на устройствах.** Самоподписанный → на Android Chrome предупреждение проходится тапом; на iOS надо установить/доверить профиль сертификата (или mkcert-CA). Это разовая процедура на семестр.
3. **Установка PWA.** Манифест + service worker у нас есть; после «Установить» Android-хром запускает приложение отдельным окном, Web Bluetooth внутри установленной PWA работает (user gesture сохраняется).
4. **Разрешения.** Android: местоположение для скана BLE в вебе не требуется (пикер системный), но Bluetooth должен быть включён. iOS: разрешение даёт сам Bluefy при первом запуске.
5. **Фон/напоминания.** PWA не умеет фоновый BLE-скан — но по v4 §5.5 это опция v2, не требование MVP. Лpush-напоминание о паре — отдельная тема (web push на iOS PWA появился в iOS 16.4+, требует установленной PWA).

## 4. Путь iOS без нативного приложения: два честных варианта

### 4.1 Bluefy как «браузер-переноска» (уже работает)

Студент ставит из App Store не наше приложение, а Bluefy, и открывает тот же URL PWA. Наш код уже прошёл этот путь (онбординг + отметка с квитанцией).

- ✅ Ноль нашей нативной разработки; один код веб-приложения на всех платформах.
- ⚠️ Это всё равно «установка приложения» (просто чужого) — «вообще без приложения» не получается, получается «без НАШЕГО приложения».
- ⚠️ Зависимость от стороннего разработчика (uptime App Store, поведение WKWebView, будущие изменения iOS).

### 4.2 Деградация канала для iOS: Wi-Fi LAN без BLE (не рекомендуется)

Теоретически iPhone-студент мог бы отмечаться по HTTP к хабу (v4 §7) без всякого BLE. Но это **ломает модель witness**: близость доказывается фактом «тот же Wi-Fi хаба», а не радио-контактом; v4 §7 прямо требует BLE-маяк как обязательное условие приёма. Отметка «из соседней аудитории с той же точкой» становится неотличимой от честной. Для MVP с претензией на доказательность — отклоняем; допустимо только как явно помеченный `needs_review`-канал в деградационной лестнице (v4 §8.9), не как основной путь iOS.

## 5. Три конфигурации «законченного MVP» и цена каждой

| | Что ставит студент | iOS parity | Наша нативная разработка | Вердикт |
|---|---|---|---|---|
| **A. Android-only чистое PWA** | ничего (URL) | ❌ нет вовсе | ноль | MVP за неделю, но iPhone-студенты мимо — в CIT это заметная доля группы |
| **B. PWA + Bluefy для iOS** | Android: ничего; iOS: Bluefy | ⚠️ через сторонний браузер | ноль | **рекомендуемый MVP**: один код, обе платформы, без нашей нативки |
| **C. PWA + наша Capacitor-оболочка** | Android: APK; iOS: TestFlight/IPA | ✅ полная | оболочка +-keychain (роадмап фазы 1/4) | целевое состояние v4 (§11 C1), но это уже «с приложением» |

## 6. Что доделать для конфигурации B (оценка: 2–4 вечера)

1. **TLS-хаб по умолчанию для LAN**: скрипт генерации сертификата (`scripts/certs.cjs` + `openssl`), README-сценарий, профиль для iPhone. Серверная часть (`TLS_CERT`/`TLS_KEY`, `ALLOWED_ORIGINS`) уже есть — надо только обвязку и доку.
2. **Детект secure context в приложении**: если `!crypto.subtle` → карточка «Откройте по https://… (сейчас http)» вместо белого экрана; это же чинит уже встреченный дефект.
3. **Карточка «Как открыть на iPhone»** прямо в приложении: шаги установки Bluefy + доверие сертификата; на Android — «Установить приложение» (beforeinstallprompt).
4. **Проверочный прогон** по матрице §2 на реальных устройствах, зафиксировать в `TESTING.md`.
5. Убрать из онбординг-подсказок APK-путь для iOS (сейчас он там неявно подразумевается).

## 7. Вывод

- «Вообще без приложения и без ограничений» — нереализуемо: Apple запретила Web Bluetooth на WebKit, обхода нет.
- «Один код PWA, обе платформы, без нашей нативки» — **да, реализуемо**: Android/десктоп — чистое PWA, iOS — через Bluefy. Это и предлагаем зафиксировать как законченный MVP (конфигурация B).
- Нативная оболочка (конфигурация C) остаётся целевым состоянием по v4 §11 и роадмапу (фазы 1/4), но не блокирует MVP: за счёт изоморфной логики фактов (принцип v4 §2.1, «транспорт сменный») переезд с PWA на оболочку позже не требует переписывания протокола.
