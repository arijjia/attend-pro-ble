# AttendPro BLE — Roadmap

Откуда: MVP завершён и закоммичен (`1ef7d9e` — хаб, PWA, Capacitor, протокол, тесты; см. `README.md` и `TESTING.md`).
Формат фаз: каждая фаза — самостоятельный релиз, откатывается одним revert'ом.

## Текущее состояние (v0.1 — MVP, готово)

- ✅ Протокол ES256/P-256: якоря-эпохи, marks, receipts, batch с merkle-корнем (fact v1).
- ✅ Хаб преподавателя: Node + bleno (GATT MTU 23, фрагментация), HTTP-консоль, хранение `hub/data/state.json` с fsync, serial-очередь, ротация эпох 5 мин.
- ✅ Студент: `$mol` PWA (онбординг по приглашению, локальная история evidence, демо-режим без радио), транспорты Capacitor / Web Bluetooth / Demo.
- ✅ Android: Capacitor-оболочка, debug APK (`dist/AttendPro-debug.apk`).
- ✅ Тесты: 7 интеграционных hub-тестов + `$mol`-набор (protocol, hub_core, student, retry) — зелёные.
- ❌ Радио-проверка на двух физических устройствах; keystore на телефоне; настоящий SSO; iOS.

## Фаза 1 — Доверие устройства и полевые проверки (v0.2)

Цель: MVP можно спокойно показать реальной паре и не бояться за ключ студента.

- [ ] **Ключ студента в Android Keystore** — перенести приватный ключ из `localStorage` WebView в `EncryptedSharedPreferences`/Keystore (ECDSA P-256, `setUserAuthenticationRequired` по возможности). Без этого любой с рутом/бэкапом получает личность студента.
- [ ] **Двухустройстная проверка по воздуху** — прогон Phone (APK) ↔ Mac (bleno) по сценарию из `TESTING.md`: онбординг в одной сети → отключение Wi-Fi → отметка по BLE → квитанция. Зафиксировать результаты в `TESTING.md`.
- [ ] **Recovery-сценарии**: потерянная квитанция (уже покрыто тестом) — проверить на железе; поведение при разряженном Bluetooth, отказе в разрешениях, смене эпохи в момент отметки.
- [ ] **Release-сборка APK** — signed release, `minifyEnabled`, запрет clear-text трафика кроме онбординга, версия/код обновления.

Критерий готовности: отметка «в воздухе» проходит стабильно 10/10 попыток, ключ переживает перезапуск телефона и не читается из бэкапа.

## Фаза 2 — Хаб как продукт преподавателя (v0.3)

Цель: преподаватель ведёт занятие без файла `admin-token` в блокноте и без ограничений single-central.

- [ ] **Мультицентральность** — очередь подключений и параллельная приём отметок (сейчас bleno обслуживает один central за раз); стресс-тест 20+ студентов, замер времени отметки на человека.
- [ ] **Консоль**: список студентов с онбордингом в реальном времени, ручной разбор «жёлтых» отметок (stale anchor), повторный выпуск приглашения, экспорт в CSV помимо JSON.
- [ ] **Аутентификация консоли** — вместо ручного копирования `admin-token`: пароль преподавателя → сессия; HTTPS по умолчанию (self-signed + QR для `ALLOWED_ORIGINS`).
- [ ] **Архив пар** — просмотр прошлых сессий (`hub/data/<session_id>.json`) прямо из консоли, сверка batch/merkle при экспорте.

Критерий готовности: реальное занятие на 15–25 студентов проходит без вмешательства в терминал.

## Фаза 3 — Университет: настоящий SSO и ведомость (v0.4)

Цель: убрать dev-срез «хаб = университет» и привязать отметки к официальной ведомости.

- [ ] **SSO-валидатор** — вынесение выпуска `device_cred`/`teacher_cred` из хаба в отдельный сервис университета (Giper Baza); хаб только проверяет цепочку.
- [ ] **Синхронизатор с Decision** — выгрузка принятых marks в ведомость университета, факт `Decision` (F7 уже есть в протоколе: `accepted/rejected/needs_review`).
- [ ] **Ротация ключей хаба** — процедура перевыпуска `hub_key_id` без потери доверия студентов (цепочка через university).
- [ ] **Публичная верификация evidence** — отдельная страница/CLI: загрузка экспорта, zero-trust перепроверка `verify_evidence` + merkle-пруфы, без доверия хабу.

Критерий готовности: квитанция студента подтверждает запись в официальной ведомости, а не только приём хабом.

## Фаза 4 — Платформы и устойчивость (v0.5+)

- [ ] **iOS** — оболочка (CoreBluetooth нет в Web Bluetooth на Safari; нативный плагин), TestFlight, оценка целесообразности.
- [ ] **Keystore на iOS** (Keychain / Secure Enclave) — паритет с фазой 1.
- [ ] **Оффлайн-устойчивость хаба** — репликация `state.json` на второй компьютер преподавателя, восстановление после сбоя питания между `accept` и `save`.
- [ ] **Наблюдаемость** — структурные логи приёма/отказов (причины `STALE_ANCHOR`, `DUPLICATE`…), метрики времени отметки.
- [ ] **Нагрузочная похожесть на прод** — лимиты ATT MTU на разных телефонах, ретраи транспорта, экономия батареи (scan settings).

## Правила движения

1. Одна фаза = один и более коммитов, каждый коммит — одна задача (откат одним revert'ом).
2. Перед коммитом: `npm run build && npm test` зелёные; радио-изменения — только с записью прогона в `TESTING.md`.
3. Секреты (`hub/data/*`, ключи подписи) — никогда не в git; `.gitignore` уже закрывает.
4. Протокол факт-конвертов (v1) не менять по мелочи: только минорные расширения через новое поле тела, несовместимое — v2 с версионным байтом.
